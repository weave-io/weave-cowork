Setting up CoWork and its agents

How you'd set CoWork up today, how easy it is to add an agent, what an agent is allowed to do, and what stops it from going out to the internet and doing whatever it likes. Answered from the code and the live checks, including where it falls short.

There are two ways to run it. To try it, run the server on your own machine. For a team, run it in a container on a server, plus a pool on a Linux machine if you want agents on demand.

Try it on your own machine

  1. Get the code and its tools

    .NET 10 SDK and bun. There's no release to download yet.

    you · once
  2. Build the web app and start the server
    cd web && bun install && bun run build && cd ..
dotnet run --no-launch-profile --project src/CoWork.Server     # http://localhost:5880
    you · 2 min
  3. Open it and set it up

    Server name, your username, display name and password. You're the admin, and you land in #general.

    you · 1 min
  4. Invite people

    Server menu → Invite people → copy the link. They open it, make an account and join.

    admin
  5. Make a project

    New project → name, a repository URL and branch (or a folder, or nothing), channels, people.

    anyone

For a team

  1. Run the server in a container
    docker compose -f deploy/docker-compose.yml up -d --build      # or podman compose

    Port 5880, the database on a volume. Put Caddy in front for HTTPS (an example is in deploy/). Add --profile voice and LiveKit's settings for voice rooms.

    admin · 10 min
  2. Open it first, before anyone else can

    The first person to open a fresh server becomes admin, so don't expose it until you have.

    admin
  3. Models, if you want agents on demand

    Server settings → Models → an OpenAI-compatible provider: a base URL and an API key (OpenRouter, OpenAI, a local model).

    admin
  4. A pool on a Linux machine with podman

    Build the sandbox image there (deploy/sandbox/build.sh), then Where agents run → Add a pool and run the command it shows. See "Add an agent".

    admin · 15 min

There are two kinds of agent. Your own runs on a machine you control, with your harness and your subscription. A team agent is a template the server starts on demand in a sandbox. Once a pool exists, team agents are much easier for everyone; your own agent has the harder first step.

Your own agent

about 10 minutes, if you build from sourceany member can do it
  1. Have a harness, signed in

    OpenCode, Claude Code through Zed's adapter, Copilot: anything that speaks ACP, on the machine where it should work.

    once
  2. Get the runner

    Build it from source (dotnet run --project src/CoWork.Runner or scripts/publish-runner.sh). There's no download from the server yet. This is the hardest step.

    once
  3. Invite an agent

    One dialog: name, about, instructions, harness command (default opencode acp), the folder it works in.

    1 min
  4. Run the command it shows
    cowork-runner connect https://cowork.example --code K7QF-2M9X

    The code works once, for 10 minutes. The dialog says "connected", and you pick its channels.

    1 min
  5. Add it to a project

    Project settings → Add an agent. You see its boundary, and choose who it takes work from.

    1 min

After that, cowork-runner run serves every agent saved on that machine. It's offline when the machine sleeps, and messages wait.

A team agent

two forms, once a pool existsadmins make templates; leads enable them
  1. Once per server: a pool and a model

    Build the sandbox image, Add a pool, run its command, set Server settings → Models. About 15 minutes, and only an admin does it.

    admin · once
  2. Make a team template

    Invite an agent → Runs on: A pool. Name, instructions, opencode acp, the image, the model.

    admin · 1 min
  3. Enable it in a project

    Project settings → Add an agent. Set its network list, setup command and budget there.

    lead · 1 min
  4. Mention it

    @researcher … in a project channel. A sandbox starts in seconds, and nobody connects anything.

    any member

Each thread gets its own sandbox. Idle ones stop and resume when someone replies; finished ones are deleted after the retention time.

An agent's permissions come from two places. CoWork decides what it can see and say. Where it runs decides what it can touch. For a team agent CoWork controls both. For your own agent, CoWork controls only the first; the second is your machine.

Your own agent (on a runner)Team agent (in a sandbox)
IN COWORK: ENFORCED BY THE SERVER FOR BOTH
SeesThe channels it was added to, and the threads it's in. Not other projects, private channels it isn't in, or direct messages. Its tools (cowork_read_channel, cowork_search) are checked against this on every call.
SaysOnly in threads it's in. It can resolve its own thread with an outcome. It can't start threads, post at the top level, or message people directly.
Takes work fromIts owner only, or the project's members (the owner chooses). Anyone else gets a short refusalThe project's members
LoopsAgent-to-agent turns stop after 3 without a person.
WHERE IT RUNS
Filesanything its owner's account can It works in a worktree per thread, but nothing stops it from reading or writing elsewhereits sandbox only A copy of the repository on its own branch, and a home folder
CommandsWhatever its harness allows. CoWork doesn't set the harness's rules: the owner's own config decides what's askedAnything inside the container. The harness doesn't ask; the container is the boundary
Networkopen Anything the machine can reachnone of its own The server, the model gateway and the project's list, through the pool's proxy. Anything else is an ask
SecretsWhatever is on the machine: its owner's sign-ins and keysOnly its thread token: one thread, one project, a new one on every resume. No model key, no GitHub sign-in
MoneyIts owner's subscription; not counted by CoWorkThe project's budget, in tokens or dollars, enforced by the gateway

How a team agent is kept off the open internet

1 · No network at allEach sandbox starts with --network none: no route anywhere, not even to other sandboxes.
→
2 · Two socketsThe pool hands it two: one to the server and its model gateway, one to the proxy. Programs inside use them as their proxy settings.
→
3 · The project's listThe proxy lets through hosts on the project's network list (for example github.com, registry.npmjs.org) and refuses everything else.
→
4 · An askA refused host becomes a card for whoever started the thread: Allow once, Allow for this thread, Deny.

The live check proved it from inside a container. With the proxy bypassed nothing resolves; through it, registry.npmjs.org answers 200 and an unlisted host gets 403. With no keys in the box, an agent that's tricked has little to steal and few places to send it.

In the order I'd do them. The first three make agents safe by default; the next three make CoWork easy to set up for someone who isn't us.
