Storing conversations as events

How CoWork stores conversation history today, why events fit it better, and what an event-sourced CoWork would look like: streams, events, projections and the hard parts.

Today CoWork is plain CRUD: tables hold the current state, and every change overwrites or deletes rows. Nothing records who changed what, or when. And the conversation isn't kept in one place: three stores each hold part of it.

Where a thread's history lives today

CoWork's database
SQLite · posts, threads, deliveries
What people see: each post's text, the tool rows (a title and a status), and the approval cards. It's a picture of the conversation, not the conversation itself.
The harness's own transcript
OpenCode's SQLite · Claude Code's ~/.claude/projects/*.jsonl
What the agent actually saw and did: the exact prompts, tool inputs and outputs, reasoning and every turn. CoWork never sees most of it, and it lives on the runner's machine.
The runner's state file
~/.config/cowork-runner/…
Which thread maps to which harness session, so a restarted runner can reload it. Lose this file and the link between thread and session is gone.

What CRUD costs us here

Today's codeConsequence
UPDATE posts SET body = body || @txtOne database write per streamed text chunk, and the post's history is its last value. A crash mid-turn leaves a half-written post with nothing saying it was cut off.
UPDATE posts SET meta=@mA tool row's start, detail and end overwrite each other. An approval card's answer overwrites the request: "who approved, and when" survives only as text in the card.
UPDATE channels SET name / topic / is_privateNo record that a channel was renamed or made private, or by whom.
DELETE FROM posts / threads / deliveries WHERE channel_id=…Deleting a channel destroys its history outright. Nothing can be undone or audited.
UPDATE deliveries SET status=…A message's journey to the agent (queued, sent, done, failed) keeps only its last state, so "why didn't reviewer answer?" can't be reconstructed.
UPDATE agents SET token_hash=…, runner_host=…No history of which machine an agent ran on, when its runner connected or left, or when its token was cut.

Live updates reach browsers as SignalR messages that aren't stored anywhere, so a browser that reconnects can't ask "what did I miss since X"; it reloads the whole channel.

Why events fit

A conversation already is a log

Messages, tool calls, approvals and turns happen once, in order, and never change. Event sourcing stores them the way they happened.

Audit comes free

With people and agents acting for each other, "who asked reviewer to push, who approved it, on whose machine" matters. Every event carries its actor and on whose behalf.

Views can be added later

Unread counts, a mentions inbox, an agent's activity, search, analytics: each is a projection built by replaying the log, even for history recorded before the view existed.

The shape

CommandsPost a message, rename a channel, answer an approval, runner reports a tool call
→
DecideLoad the stream (or its small state), check the rules (membership, owner-only answers, loop limit), emit events
→
Event storeAppend-only, one transaction, optimistic concurrency per stream
→
ProjectionsFeed and thread views, channel list, members, unread, audit, search
→
LiveBrowsers and runners catch up from a position: "everything after 18,204"

The event store: one table

CREATE TABLE events (
  position      INTEGER PRIMARY KEY AUTOINCREMENT,  -- global order, what subscribers catch up from
  stream_id     TEXT NOT NULL,                      -- 'thread-42', 'channel-3', 'agent-7', 'server'
  version       INTEGER NOT NULL,                   -- per stream; UNIQUE(stream_id, version) = optimistic concurrency
  type          TEXT NOT NULL,                      -- 'MessagePosted', 'ToolCallFinished', …
  schema        INTEGER NOT NULL DEFAULT 1,         -- for upcasting old events
  data          TEXT NOT NULL,                      -- JSON
  actor_id      INTEGER,                            -- who did it: a person, an agent, or null for the server
  on_behalf_of  INTEGER,                            -- the person whose request an agent is acting on
  correlation   TEXT,                               -- the turn this belongs to (one mention → one turn)
  causation     INTEGER,                            -- the event position that caused this one
  occurred_at   INTEGER NOT NULL,
  UNIQUE (stream_id, version)
);

SQLite in WAL mode handles this comfortably at team scale. The same table moves to Postgres unchanged; or, on .NET, Marten (MIT) gives event streams and projections on Postgres ready-made.

Live updates become catch-up

After a commit, the server pushes the new events (already shaped for the screen) over SignalR, each with its position. A browser or runner that reconnects says "I last saw 18,204" and gets everything after it. No full reload, and no gaps. The same applies to runners: deliveries become events the runner reads from its position, which replaces today's deliveries status table.

What it answers that today's tables can't

"Why did reviewer run git log?"

#14 was caused by #13 (Alex allowed it), which answered #12, raised in turn t2, which Rosa started at #10. That's one causation chain.

"What did the thread look like before reviewer answered?"

Replay thread-42 up to #7. The same replay powers "what you missed" and debugging a bad turn.

A stream is one thing whose rules are checked together. Keep them small: a thread, not a channel's whole history, so appends don't fight over one version number.

Not events

Streaming text deltas

The tokens of an answer go to browsers live but aren't stored one by one. The answer is stored as AgentReplied segments: one at each tool boundary, and at the end of the turn.

Voice presence

Who's in a call right now is volatile state. Only VoiceCallStarted and VoiceCallEnded (with who took part) are worth keeping.

Secrets

Password hashes and token hashes stay in a small table of their own, never in the event log, which should be safe to export.

The harness keeps its own transcript
Event sourcing in CoWork doesn't capture what the agent saw: OpenCode and Claude Code keep their own history on the runner. Two ways: record the facts (prompts delivered, tool names and inputs, output size and hash, replies, approvals), which is enough for audit, or also ship tool outputs, which is complete but large and may carry secrets from the owner's machine. Recommend the facts, with tool output opt-in per agent.
Partial answers on a crash
If text deltas aren't events, a server crash mid-turn loses the unsent part of an answer. Segmenting AgentReplied at tool boundaries (plus every ~5 s of text) bounds the loss, and recovery appends TurnInterrupted, so the thread says honestly that it was cut off.
Deleting and forgetting
An append-only log and "delete this" pull against each other. Normal deletes become events (ChannelDeleted, MessageDeleted) and projections hide them; the audit keeps the fact. Real erasure, for a person who leaves or a secret pasted by mistake, needs either a purge tool that rewrites the stream or per-stream encryption keys you can destroy ("crypto-shredding"). Recommend MessageRedacted (data replaced, event kept) now; crypto-shredding if it's ever hosted for others.
Changing event shapes
Events live forever, so a changed shape needs an upcaster (old JSON to new) keyed on schema. Keep events small and named in past tense for facts; never put view-only fields in them.
Rebuilding projections
Replays must be cheap: projections are tables keyed by a checkpoint position, rebuildable from zero. Tests replay fixtures of events and compare the views, which is also how today's journey checks stay meaningful.
Concurrency
Two replies in one thread race on its version: retry the append (posting has no rule that can fail). For turns, "one turn per agent per thread" is checked from the stream, which replaces today's queue status updates.
Size
A busy team posts tens of thousands of events a month; SQLite handles millions. The cost to watch is tool output if shipped (above), not the log itself.

It's worth doing now rather than later: the prototype has no real data to migrate, and every feature on the "what's next" list (unread, inbox, audit, agent activity, resolving threads) is a projection over these events.

Decisions for you

1 · Where the events live

AOne events table in SQLite, our own small store, with Postgres later. No new dependency. Recommended for now
BMarten on Postgres: mature .NET event sourcing and projections, but Postgres becomes a requirement for self-hosting.
CKurrentDB (EventStoreDB): purpose-built, but one more server to run.

2 · How much of the agent's work CoWork records

AThe facts: prompts, tool names and inputs, output size and hash, replies, approvals. Tool output opt-in per agent. Recommended
BEverything, tool output included: a complete record, but large, and it may carry secrets from the owner's machine.

3 · Streaming text

ASegments at tool boundaries and every ~5 s; live deltas aren't stored. Recommended
BEvery delta as an event: exact replay of the typing, at many times the volume.

4 · Forgetting

ARedaction events now (content replaced, fact kept); crypto-shredding only if it's hosted for others. Recommended
BCrypto-shredding from the start.
