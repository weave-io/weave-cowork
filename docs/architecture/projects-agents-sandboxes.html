Projects, agents and sandboxes

How a team installs CoWork, brings people and agents in, and works on projects with them: the scenarios, the model underneath, where an agent's boundary is, and whether CoWork should start agents itself. Ends with the decisions taken, the mockups to test them and the slices to build.

One idea runs through all of it: an agent's definition, the place it runs and the project it works on are three separate things. Today they're fused: an agent has one runner and one workspace folder. Pull them apart and inviting, provisioning, sandboxing and "a project on a directory" all fall out of the same model.

The questions

How do we install CoWork?
docker compose up today; add a single-file server for a laptop trial. The first visit should need a setup token the server prints, so a public URL can't be claimed by whoever arrives first. Getting started
What's the first-run experience?
A short wizard: server name, your account, how people sign in, where agents run, a first project. Then a checklist in the app until each is done. Getting started
How do I invite people?
Invite links (built), plus links scoped to one project for guests, and "anyone signing in from @lumenlabs.example joins" once single sign-on is on.
How do people authenticate?
Local passwords (built), then OpenID Connect (Google, Microsoft, Keycloak, Authentik) and passkeys. Agents never sign in like people: they hold a key, and their reach outside CoWork comes from credentials given to their sandbox.
What is a channel?
A place for conversation, text or voice. Only that. It doesn't own a directory, agents' permissions or a budget. Projects, channels, threads
What is a project? Is a channel a project?
No. A project holds channels, and owns what isn't conversation: members, workspaces, sources, agents, rules and a budget. A small project has one channel and feels like one. In Discord terms it's a category that grew settings.
What is a thread? Does it make sense?
Yes. It's one piece of work, and for an agent one session. It needs a title, a status (working, waiting for you, done) and an outcome (a summary, a branch, a document). Without those, threads are chat that gets lost.
Can a project sit on a directory?
Yes, as a workspace: a git repository (portable, any sandbox clones it) or a folder on a named machine (only agents on that machine can use it). Each thread gets its own worktree and branch, so parallel threads don't collide. The workspace moves from the agent to the project. Sandboxes
What does an agent need?
An identity and an owner, instructions, an ACP harness and model access, a place to run, and grants: projects, channels, who may give it work, who approves, what it may touch. Agents
How does an agent take part?
Mentioned in a channel it's in, it opens a thread and works there. Later it also starts threads itself, watches for events (CI failed, issue filed) and works on a schedule, all within limits.
What's the sandbox story?
Layers: its own home, only the project's workspace, an egress allowlist, secrets that never enter as raw keys, owner approvals, and changes leave as branches. On your own laptop it's optional and labelled; for provisioned agents it's always on. Sandboxes
Invite agents, or provision them?
Both, one model. An agent template plus a placement: pinned to a runner its owner connects (invite, built), or a pool that starts a sandbox per thread on demand (provision). CoWork's control plane is small: a pool is a runner that can start containers, and later a cloud provider behind the same contract. Control plane

Two kinds of agent identity, kept apart. Who the agent is to CoWork (its key: which channels, which threads) and what it can reach outside (a GitHub token, a model key, a Notion connection). The first lives in CoWork. The second belongs to the sandbox or the runner, and CoWork only brokers it.

How do people actually work on projects? A project has a goal, a team, material (code, documents, data) and a stream of small pieces of work: questions, research, changes, decisions. Conversation is how the work gets coordinated, not the work itself. So the conversation lives in channels and the work lives in threads, and both sit inside a project that owns the material.

Three options for "project"

A · A channel is a project

Simplest. Slack teams do it by naming (#proj-checkout).

Breaks at once: projects want several channels (a voice room, alerts, a guest channel), and the workspace, sources, budget and rules then hang off one of them.

B · A project holds channels Chosen

A category with settings. Its channels share members, workspaces, sources, agents and rules. A new project gets one channel named after it; most will never need more.

Channels outside any project (#general) stay server-wide.

C · A project is a server

Discord's answer. Strong walls.

Too heavy: people, agents and runners would be set up again per project, and nothing crosses between them.

Threads as work

A thread is the right unit: small context, one session, side by side with others. What's missing is that a thread is treated as chat. It should carry what a task carries.

Status, shown everywhere

working waiting for Alex blocked done on the post, in the channel and on the project's board. People notice "waiting for you" without reading.

An outcome

When an agent finishes, it resolves the thread with a summary and its artefacts: a branch, a pull request, a document in the library. The outcome is what search and the board show.

A project board

Every thread in the project, by status. "What's going on in Checkout?" answered without scrolling channels. It's a view over threads, not a second task system.

Threads without a post

"New task" on the board, a webhook, a schedule or another agent can start one. It still appears as a post in a channel, so the conversation stays the record.

Direct messages

A DM with an agent is a private channel of two, outside any project: your own assistant, with your own memory. It can't see any project's material until you start the thread from inside the project.

Three kinds of agent

Personal

Alex's own Claude Code on his laptop, brought into a project. His subscription, his machine, he approves. Offline when his laptop sleeps. This is today's model.

Team template

"researcher", "reviewer", "triage": defined once on the server (instructions, harness and version, image, tools, default rules), enabled per project, started on demand in a sandbox. Owned by the project; the person who asked or a project lead approves.

Visiting

Another team's agent, shared with an invite link. Keeps its owner, key and runner; joins one project like a guest.

The boundary of an agent

Every agent should be able to show its boundary in plain sentences, on its profile and when someone adds it to a project. If we can't write the sentence, the rule isn't clear enough to enforce.

What happens today

The harness runs as the runner's user, in the agent's one workspace folder, for every thread (AcpAdapter.cs uses m.Workspace as each session's cwd). Two threads editing at once share the same files, and the harness can reach anything the runner's user can. The mockup promised "a worktree per thread"; that isn't built.

On your own runner the sandbox is a choice (cowork-runner run --sandbox), and when it's off the thread says so: "runs unsandboxed on alex-laptop". People asking someone's personal agent to do something should know whose machine they're touching.

A project on a directory

A repository Default

git@github.com:lumen/checkout-app, branch main. Any runner or sandbox clones it once and makes a worktree per thread on cowork/<thread>. Works with provisioned agents, survives machines, and the result is a branch someone can review.

A folder on a machine

~/source/checkout-app on build-01. Only agents whose runner is on build-01 can work here; adding another agent says "researcher can't reach this folder". Worktrees per thread if it's a git folder; otherwise shared, read-only unless the project allows writes.

A project can have several workspaces (app, docs, a read-only data folder). The agent no longer has a workspace of its own: the agent says how it works, the project says what it works on. The same reviewer in two projects gets a different cwd per thread.

Your worry is right: if starting research means creating an agent, finding a machine, running a command and inviting it, nobody will do it twice. But "only provision" loses something real: people want to bring their own agent, with their subscription and their machine. So both, as two placements of the same thing.

The smallest control plane

CoWork shouldn't grow into a scheduler. It needs one contract, kept as small as the runner's: start a sandbox for (template, project, thread), stop it, tell me its state. Inside the sandbox is the same cowork-runner, which connects out with a token minted for that one thread. No open ports, and the server holds no cloud credentials.

Lifecycle

A sandbox per thread Chosen

Strong isolation, threads run in parallel, nothing leaks between pieces of work. Its volume (worktree and the harness's own data) is kept, so a reply after it stopped resumes with session/load. Stops after 15 minutes idle; deleted some days after the thread is done.

Costs a cold start per thread: seconds with a warm image.

A sandbox per agent and project

Warm, one clone, threads share a machine with a worktree each.

Fewer starts, but one bad thread can affect the others, and memory piles up on a 14 GB host.

Money and limits

Provisioned agents spend the server's money, so they need what personal agents don't:

A model gateway

The server holds provider keys; sandboxes get a per-thread token to a small proxy in CoWork that forwards and meters. Keys never enter a container, and spend is known per thread, agent and project.

Budgets

Per project a month, per thread a cap. At 80% the project's leads are told; at 100% new threads wait for a lead to raise it.

Who may start agents

A project grant ("members may start researcher"). Agents starting agents: depth 2, and the agent-to-agent turn limit (built) still holds. A Pause button for every agent in a project.

Connecting sources

People don't keep a project in one place: a repository, documents in Drive or Notion, issues in GitHub or Linear, a shared folder, the web. Agents pull from them with tools, as AGENTS.md says. The mechanism already exists in ACP: session/new takes a list of MCP servers, and CoWork passes an empty one today.

The trap: a connection made with Rosa's account, used by an agent anyone in the project can ask, lets Sam read what Rosa can. A connection's page says whose it is and who can reach it through agents, and personal connections are off for guests' requests.

Search

People search

Posts, threads by outcome and status, the library, people and agents. Filters: in:#checkout-app, from:@reviewer, project:checkout, is:waiting. SQLite FTS5 over the projections we already build from events. Results respect what you may see.

Agent search

The same index as a cowork_search tool, limited to the agent's boundary. "What did we decide about refunds?" goes to a thread with an agent that searches, reads and answers with links.

Thread outcomes do the heavy lifting: searching a summary finds the decision, where searching chat finds the argument about it.
