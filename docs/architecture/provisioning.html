How a provisioned agent works

What happens between Rosa typing "@researcher …" and an answer, when no runner is serving researcher and nothing is running yet. One request, step by step, across every part involved. Then what has to be set up once, how it differs from today's pinned agents, and what happens when things go wrong.

The idea in one sentence. The server never starts anything itself: a pool, a runner on a Linux box that has already connected out to the server, starts a container for the thread, and the ordinary runner inside that container connects back in with a token good for that one thread. From then on it's the same as today's agents.

Click any arrow, or use ← and → on the keyboard. exists works like this today; new is to build.

Four things exist before Rosa can ask. Steps 1 to 3 are done once per server by an admin; step 4 once per project by its lead.

1Connect a pool

On any Linux box with podman, the admin runs the runner in pool mode with a one-time code from Where agents run → Add a pool:

cowork-runner pool connect https://cowork.lumen.example \
  --code K7QF-2M9X --slots 4 --memory 2500M

It enrols like a runner today, but its token may only start and stop sandboxes. It serves no agent itself and holds no agent's identity. It shows as pool-01 · 4 slots · online.

2Add model access

Server settings → Models: a provider and its API key (Anthropic, OpenAI, OpenRouter, a local model). The key stays in the server. Sandboxes reach models only through the gateway with their thread token.

Subscriptions (a Claude or ChatGPT plan) can't be shared this way: they stay with pinned agents on their owner's machine.

3Make a template

Agents → New team template: researcher. Instructions, the harness (opencode acp 2.4.1), its model through the gateway, and the sandbox image it starts from (see the Images tab).

4Enable it in a project

In New project or the project's settings, Alex switches researcher on for Checkout app, with a budget. Checkout app's workspaces, sources, rules and network list then apply to every researcher thread there.

That's all. Nobody connects anything per thread.

Both are agents with a handle, instructions and an owner. They differ only in where the harness runs and who pays.

A sandbox is a container, and a container starts from an image: a packaged copy of a Linux filesystem with programs already installed. It's what podman run takes, the same thing a Dockerfile builds. Everything the agent can run in its sandbox has to be in that image, or be installed after it starts.

The real question: the project's own tools

reviewer working on a .NET repository wants the .NET SDK to build and run the tests. A web project wants bun. The stock image has neither. Three ways to get them there:

A · Stock image plus a setup command Recommended

The project's settings hold a setup command, such as scripts/agent-setup.sh, that installs what the repository needs. It runs once when a thread's sandbox is first made, and its result is kept in the thread's volume, so later starts skip it. The package registries must be on the project's network list.

Simple and per project. The first start of a thread is slower.

B · The repository's devcontainer

If the repository has .devcontainer/devcontainer.json, the pool builds an image from it, adds the runner and the harness, and caches it per commit.

Reuses what many teams already keep. Building images on the pool is slow and heavy on a small box.

C · A Dockerfile per template

The template's author writes the image.

Most control, but tools belong to the project, not the agent: researcher on two repositories would need two templates.

Agent Substrate works the same way: an ActorTemplate is an image too. Whichever we pick carries over.

Agent Substrate is Google's runtime for stateful agents on Kubernetes (a CNCF sandbox project, 1.0 on 5 November 2026). It does at cluster scale what CoWork's pool does on one box: one sandbox per piece of work, suspended when idle and resumed on the next request, with egress rules and secrets that never enter the sandbox. Facts below are from its docs (architecture, credential injection).

The one real difference

CoWork: the runner calls out

The runner inside a sandbox connects out to the server and keeps that connection open. Messages come down it. No inbound port anywhere.

Substrate: requests come in

A request with header ate-target-actor reaches the actor through its router, which wakes it first. A long-held outbound connection and snapshots don't mix well: a resumed sandbox would find its connection dead.

So the runner needs a second way to receive work: a small HTTP endpoint that takes a message and streams the agent's events back. The messages stay exactly the ones in CoWork.Contracts; only the transport differs. The podman pool can keep using the outbound connection.

What we take now

Its shape for our contract

Create, resume, suspend and delete a sandbox; states suspended, resuming, running. Network rules and credential references as data in the same shape as its EgressPolicy (hostnames, then replaceHeaders with header, prefix and a reference). A Substrate provider is then a translation, not a redesign.

Credentials by placeholder

Grow the model gateway into the proxy's job: for a listed host, replace a placeholder header with the real secret. Model keys first (no TLS interception needed: OpenCode is pointed at the gateway), GitHub and sources in a later slice with a CoWork CA in the image.

Signed thread tokens

Make the thread token a signed JWT with audiences (server, gateway, proxy), so a pool's proxy can check it without a call home.

Verdict

Build the podman pool first, shaped like Substrate. Add a Substrate provider when a team running CoWork has a Kubernetes cluster. Substrate needs Kubernetes, Postgres, GCS or S3 and gVisor or Kata: far from CoWork's one-box docker compose up. Its memory snapshots and density are real gains at scale, and the provider would be about one to two weeks once our contract has its shape. Google's Agent Executor (AX), built on Substrate, overlaps with our templates and workspaces and says it expects breaking changes: watch it.

The runner already runs whatever the server sends it (DeliverMessage carries the instructions, harness command and workspace), so the runner inside a sandbox is today's runner. What's new is around it.
