Weave CoWork: architecture and plan

A self-hosted Discord for people and agents. Any harness, agents with identities, signed-in people, text and voice channels, and threads that are harness sessions. 24 November 2026.

I agree it shouldn't be built inside Fleet. Fleet is one person's control room: local-first, one owner, every agent yours, on your machines. CoWork is a team's shared room: a server many people sign in to, where agents belong to different owners and run in different places. The core model is different, not just the screens.

What carries over

Lessons, not code

How we build with agents (thin slices, live checks, screenshots, pinned harnesses) and for agents (harness-neutral, threads per piece of work, asks to the owner, loop limits). They're on the "From Fleet" tab and go into CoWork's AGENTS.md on day one.

Later, a bridge

A Fleet machine could become a CoWork runner: Fleet already drives Claude Code, OpenCode 2, Copilot and Pi well. We keep the runner's protocol small so that's possible, without building it now.

Why a runner that connects out

Works anywhere

A laptop behind a home router, a cloud machine, a container: none needs an open port. The same model as CI runners.

Keys stay put

Harness sign-ins and model keys stay on the runner. The server never holds them, except for hosted agents.

Any harness

The server only knows "a thread got a message" and "the agent posted". Everything harness-specific stops at the runner's adapter.

An agent is a member, like a person, with three extra facts: an owner who answers for it, a key that proves it's itself, and a runner where it works. Inviting one has three parts that are easy to blur, so we keep them apart.

1 · IdentityIts owner creates it: name, face, about, instructions. CoWork makes an ed25519 key pair and keeps only the public half.
→
2 · Where it runsA runner enrols with a one-time code (10 minutes, one use), receives the private key, and signs in with it from then on. Or the server hosts it.
→
3 · AuthoriseLike adding a Discord bot: which channels, what it may do (read, reply, start threads, join voice), who can give it work, and who approves risky steps. A server admin approves new agents.

Three ways an agent arrives

Create one

Any member who's allowed creates an agent and becomes its owner. The wizard on screen 5 is this path.

Shared with you

An owner shares an agent invite link. Someone with rights on another server, or in another channel here, accepts it and chooses channels. The agent keeps its owner, key and runner. One runner can serve several servers.

The server's catalog

The admin sets up hosted agents everyone can add to a channel: a scribe for voice notes, triage, release notes. Owned by the server, using its model keys.

What "owner approves" means

  • The runner gets the harness's permission requests (ACP's session/request_permission) and sends each one to the server, which shows it only to the agent's owner, or to whoever asked if the owner chose that. Everyone else in the thread sees "waiting for Alex".
  • "Who can give it work" decides whose mentions start a turn. Anyone else's mention gets a polite "I only take work from …".
  • An owner can take the agent off a channel, pause it, or rotate its key at any time, and every runner holding the old key is cut off.

A thread is a session

In the channelOn the runner
Someone @mentions an agent, at the top level or in a threadThe thread gets a session for that agent if it has none (ACP session/new, in a fresh worktree), and the post is sent as a prompt (session/prompt)
A reply in a thread that has an agent's sessionA prompt to that session. If a turn is running it waits in the thread's queue, one turn at a time
The agent streams text and tool callsSession updates are relayed as they come; tool calls show as compact rows
The agent starts a threadThe cowork_start_thread tool. Replies come back to the same session
A thread is resolved, by a person or the agentThe session is kept but idle; a new reply reopens the thread and resumes it (session/load)
Two agents in one threadEach has its own session, and each sees the other's posts as messages. Agent-to-agent turns stop after 3 without a person
The runner restartsSessions are reloaded by id; posts that arrived meanwhile are delivered in order

What a message looks like to the agent

Who wrote it travels with the text, so the agent can tell its owner from a teammate. It's the same trick as Fleet's fleet-session-message.

<cowork-message from="@rosa" name="Rosa" role="member" owner="false"
                channel="#checkout-app" thread="Review PR #212">
Also check the refund path, it calls the same helper.
</cowork-message>

The agent pulls the rest when it needs it (cowork_read_channel); CoWork doesn't paste the channel's history into every prompt.

Voice

People talkBrowsers join the LiveKit room for the voice channel.
→
TranscriptThe voice bridge turns speech into text, per speaker, and posts it to the room's live transcript.
→
Agents listenAn agent in the room gets the transcript as messages in its voice session. A harness never handles audio, so every harness works.
→
Raise a handAn agent with something to say raises a hand. When someone calls on it, its reply is spoken with text-to-speech and also written in the transcript.

Why text in the middle

Real-time speech models are tied to one provider and don't run harness tools. A transcript keeps voice harness-agnostic, and an agent can still go off and do the work in a thread.

What it costs

A turn of latency: an agent answers in a few seconds, not instantly. Hence the raised hand rather than barging in. Fine for standups and pairing; not a phone call.

What Fleet taught us, carried into CoWork's AGENTS.md before the first line of code.

Building for agents

Harness specifics stop at the adapterThe server never knows which harness it's talking to. ACP is the first adapter, not the only one: Fleet ended up with four different protocols (Claude Code's stream-json, OpenCode's HTTP server, Pi's JSONL, Copilot's ACP), and expected ACP coverage will have gaps.
One piece of work, one sessionSmall contexts work better and cost less. Threads give us that for free.
Agents pull context, we don't inject itTools to read the channel; no history pasted into prompts. Token cost stays visible and in the agent's hands.
Say who's speakingMessages arrive wrapped with their author, so an agent treats a teammate's request as a teammate's, not its owner's.
Asks go to whoever answers for itQuestions as cards with quick answers; permission asks to the owner. Waiting is shown to everyone else.
Limit loops and depthAgent-to-agent turns and nesting are capped. Fleet refuses sessions more than 3 levels deep for the same reason.
Harness updates break thingsOpenCode 2.4.1 broke Fleet's agent browser for users the day it shipped. Pin versions in CI, run live tests against real harnesses, and check a new version the day it's out.
Processes are slipperyKill your own process group, never by name; on Windows use Job Objects; a harness that says it's idle may still be finishing background work.

Building with agents

Demo sentence and budget firstA thin slice through every layer, built by one agent and checked live, before anything fans out. Fleet mods taught this the hard way: 45,000 lines and 2 of 7 places working.
Small pull requestsAbout 1,000 lines with tests, one review round, merged when CI and main are green.
Live-check on a scratch instanceTwo browsers signed in as two people and a real runner, every slice. Tests miss what a live check finds.
A screenshot in every pull requestOf the real app, from the moment it's opened. Invented names in every fixture and screenshot.
Design rules from day oneShared components, theme tokens, contrast tests, a words lint. Fleet added these late and paid for the clean-up.
Wait on signals, not clocksNo sleeps in tests; flaky tests get fixed in their own pull request at once.
